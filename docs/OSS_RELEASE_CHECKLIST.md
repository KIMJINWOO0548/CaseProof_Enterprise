# Open-source repository and distribution readiness

This is a checklist for a repository owner, not a record that these actions were performed. The v5.3 archive is a development handoff; it does not publish a repository, upload a package, or establish production readiness.

## Before making a repository public

- [ ] Confirm ownership and redistribution permission for inherited code, fixtures, and prose. Resolve every entry in `THIRD_PARTY_NOTICES.md`; remove unverified external assets.
- [ ] Review the staged files and full Git history for credentials, private data, database files, generated token output, and third-party binaries. The included ignore rules do not remove content already tracked.
- [ ] Accept the Apache-2.0 license choice for original material and record accurate attribution. Do not invent a legal entity or maintainer address.
- [ ] Appoint a maintainer and a private security reporting route. Enable and test GitHub private vulnerability reporting, then update `SECURITY.md` with the actual route.
- [ ] Provide a private conduct-reporting route and a responsible reviewer in `CODE_OF_CONDUCT.md`.
- [ ] Enable GitHub Actions and the dependency graph. Enable available Dependabot/secret-protection settings, reviewing permissions and plan availability.
- [ ] Run CI on the actual target repository and commit. Configure branch protection/rulesets to require the applicable checks only after observing their real names and results.
- [ ] Check the README's clone/install examples against the chosen repository identity; this package intentionally supplies no invented remote URL or status badge.

The root CI workflow has `contents: read`, no repository secrets, no publishing steps, and no `pull_request_target` trigger. It uses commit-pinned actions and separate jobs. Audit the workflow before enabling any future credential-bearing job. Uploaded evidence is limited to explicit synthetic-test reports, dependency versions, and advisory results; retention is 14 days.

## What CI does

| Check | Scope | Limitation |
| --- | --- | --- |
| Python 3.11, 3.12, 3.13 matrix | Hash-locked dependencies, package contracts, pytest, synthetic HTTP/SQLite smoke | Configuration alone is not a passing run; no PostgreSQL or browser certification |
| JavaScript syntax | Node.js 22 parses the static UI code | Does not exercise clicks, accessibility, or real browser rendering |
| Source archive/wheel | Required assets and licenses; fresh wheel installation; static HTML, health and temporary seed outside checkout | Does not qualify the service for production |
| OSV audit | `pip-audit==2.10.0`, exact locked development dependency set, strict collection, no ignored advisories | Known Python-package advisories only; network/service failure fails the check; tooling's own dependency tree is not fully locked |
| Dependency review | Public-repository pull request dependency diff, failure at low severity or above, no PR comment writes | GitHub dependency graph is required; skipped on private repositories; OSV still runs |

No check uses `continue-on-error` to hide a failure. Resolve an advisory through a reviewed dependency update, or record a time-bounded, advisory-specific exception with a responsible owner before changing scan policy. A passing scan is not a claim of absence of vulnerabilities. Dependency review is an additional GitHub-native diff check; OSV scans the recorded dependency set even when no dependency file changed.

## Local Docker demonstration

Docker Engine with the Compose v2 plugin is required. The image is non-root and the compose configuration publishes port 8000 on IPv4 loopback only. Credentials are generated by a separate one-off command; they are not committed or printed by normal service startup.

```bash
docker compose build
docker compose run --rm --no-deps caseproof-demo python -m service.cli init-demo --database sqlite:////data/caseproof.sqlite3
docker compose up -d
```

Keep the one-time tokens in a private location for the demo, then open `http://127.0.0.1:8000/`. Do not capture the initializer's output in a public report or shared terminal transcript. Initialization does not repeat tokens for existing accounts. Losing them requires a deliberate reset of the disposable synthetic database; never apply a reset command to valued data. `docker compose down` stops and removes containers while retaining the named volume.

The Docker health check tests only `/api/health`; it does not prove tables are initialized or audit records are intact. This image is for a single-worker local demo, not an Internet service. Do not override loopback binding to expose it remotely.

## Before distributing a built artifact

- [ ] Run the Python matrix, tests, package checks, and installed-wheel check on the release commit; record exact commands and results.
- [ ] Independently reproduce local installation and the browser workflow. Mark unavailable checks as `NOT_RUN` with a reason.
- [ ] Review unresolved prebuild gates, known findings, and the release notes; distinguish inherited runtime behavior from future design.
- [ ] Review runtime, build, and transitive dependency licenses for the exact lock; preserve required notices in any redistributed image.
- [ ] For a container image, resolve and pin `PYTHON_IMAGE` to a reviewed digest, rebuild, and separately assess operating-system packages. The default minor tag is intentionally not a reproducible image identity.
- [ ] Build from a clean checkout and inspect wheel/source contents. The wheel includes `service`, `reference`, synthetic JSON data, static UI, and license files; tests and handoff documents remain in the source archive/repository.
- [ ] Verify version consistency and regenerate release integrity manifests after the final file changes. Hash manifests prove content consistency, not trustworthiness.
- [ ] Attach only evidence from this exact run. Never attach unreviewed databases, raw tokens, customer files, or historical logs as fresh proof.
- [ ] If later publishing to a package registry or container registry, establish the real account/name, review permissions and signing/provenance requirements, and obtain the owner's authorization for that publication.
