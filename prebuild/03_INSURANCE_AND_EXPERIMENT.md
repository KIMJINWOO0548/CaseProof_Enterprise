# 보험 업무 검증과 비교실험 계약 v5.3

> 본 문서는 **실험 계획**이다. 현재 20건은 작성자가 만든 합성 사례이며, 독립 실무자가 검수한 정답이나 360건 블라인드 세트가 아니다. 실제 회사의 약관·고객·지급 결과라고 표시하지 않는다.

## 1. 평가할 업무 범위

초기 사례는 가상 보험상품의 청구서류 기한 등 **텍스트 답변의 숫자 주장과 관련 근거**다. CaseProof는 지급 가능액, 인수 승인, 보험료를 결정하거나 고객에게 실제 계약 결론을 제공하지 않는다. 가짜 모델·합성 문서로 시작하고, 실제 모델 연결은 별도 Gate다. 보험 업무 전문가와 인터뷰해 업무 흐름·정답·개선 가치·제품 수요를 구분한다.

### 핵심 개체와 시간

- `source`: 저작권·사용 권한·출처 ID·원문 hash·발행사·상품 및 약관/특약 범위. 출처 상태 DRAFT / PUBLISHED / REVOKED와 승인 주체·시각을 기록. 상태 이력도 시간축을 가진다.
- `policy_version`: 상품/보장/특약/업무범위, 약관 버전 ID, 유효 기간 `[valid_from, valid_to)`, 시스템 지식의 기간 `[recorded_from, recorded_to)`, 개정 이전 관계, 소급 정책 ID, 검토자. 시간대가 들어가는 timestamp는 offset 포함, 날짜는 정확한 업무 timezone 기준 별도 명세.
- `case_context`: tenant·상품·업무, 계약 체결/유지·사고·청구·상담 날짜, 특약 가입·해지 사실 및 `rider_context_status` (`CONFIRMED`, `UNKNOWN`). confirmed+빈 목록과 unknown은 다르다. 누락·모순은 설명과 함께 보류.
- `resolution`: `RESOLVED`, `INCONCLUSIVE` 및 이유; 룰/버전/출처 ID, 적용일 종류·값, 근거 clause 및 검증 시점. 질문에 없는 지급 판단을 만들지 않는다.
- 출처 승인 시각과 적용 시각은 다르다. 과거에 알려졌던 내용으로 평가하는 것과 사후에 정정된 현재 지식으로 과거 사실을 해석하는 것은 서로 다른 as-of를 명시한다. 한 가지 시점만으로 전부 처리하지 않는다.

## 2. 꼭 검증할 데이터 분류

| 분류 | 예시 | 허용 판정 |
|---|---|---|
| 유효 기간 경계 | 개정 전날·당일·다음날 | 각 업무팩이 정한 기준일에 따라 선택, `[start,end)` |
| 서로 다른 날짜 | 계약 6/30·사고 7/01·청구 8/01 | 질문별 필요한 날짜를 확정할 수 없으면 INCONCLUSIVE |
| 기록 시점 | 실제 적용일 전에 알려지지 않았던 개정 | 요청한 as-of 시점의 지식만 사용. 과거와 현재의 차이 설명 |
| 미승인/철회 | 요청한 지식 시점에서 정본이 DRAFT 또는 REVOKED | 미승인 근거를 근거로 PASS 금지 |
| 특약 | 가입 확인됨/미확인/unknown 특약/동일 우선순위 | 미확인 또는 영향 불명 미승인 상위 특약은 INCONCLUSIVE |
| 소급 개정 | 변경이 과거 계약에 적용되는지 문서가 불명 | 비소급/소급 임의 단정 금지; 담당자 검수·정책 버전 |
| 충돌 | 동일 적용 범위에서 우선순위 같은 상충 규칙 | POLICY_CONFLICT, 담당자 검토 |
| 상품·보험사 혼입 | 다른 tenant나 유사 상품의 동일 clause ID | tenant/product/source 정합성 불일치 시 사용 금지 |
| 출처 위조 | 응답이 없는 문서·문단·버전을 인용 | 인용 식별자·원문 hash·접근 범위 검증 실패 |
| 추가 문장 | 숫자는 맞지만 다른 핵심 문장이 근거와 모순 | '숫자 하나 일치'만으로 답변 전체 PASS 금지. 현재 MVP는 숫자만 다룬다는 범위 명시 |

합성 예시에서 어떤 기한·소급 해석이 실제 약관의 법적 정답인지 여기서 정하지 않는다. 공개 약관을 쓰더라도 해당 버전·사용 권한·계약 맥락·전문가 검수를 확보해야 하며 업무에 바로 사용하지 않는다.

## 3. 360건 고정 split — 계획 정본

기존 문서의 여러 분할안보다 이 문서의 **160 개발 / 80 검증 / 120 블라인드 테스트 = 360**을 우선한다. 이 숫자는 목표이고 실제 작성·검수·봉인 전에는 0건이다. 360이라는 수만으로 충분한 통계적 검정력·보험 업무 적합성이 보장되지는 않는다.

1. **개발 160:** 개발과 디버깅용. 모델 출력에 맞춰 정답을 바꿔서는 안 된다.
2. **검증 80:** 모델·평가기·임계값의 제한적 선택에 사용. 최종 결과로 제시하지 않는다.
3. **블라인드 120:** 담당자와 평가 실행자를 분리한다. 문서 원본·상품 가족·동일 계약/사고·시나리오 파생형 단위로 group split하여 유사 사례가 여러 split에 섞이지 않도록 한다. 정답·실제 기대 원문을 모델 프롬프트에 전달하지 않는다. 결과 분석 후 사례를 이용해 수정을 반복했다면 해당 세트는 더 이상 미노출 테스트가 아니므로 새 holdout이 필요하다.

### 데이터셋 레코드 최소 계약

`case_id, pack_id, synthetic=true, scenario_family, product_id, query, context_snapshot, rider_context_status, source_version_ids, source_hashes, business_as_of, recorded_as_of, ground_truth_status, expected_claim_or_constraint, expected_reason, allowed_citation_spans, severity, annotator_ids, adjudicator_id, rubric_version, dataset_version, split, gold_freeze_hash`. 이 hash는 자기 자신을 포함하지 않는 정규화 payload를 고정된 UTF-8/키 순서/버전/케이스 정렬로 직렬화해 계산하며, envelope의 hash 필드는 입력에서 제외한다.

개인정보나 실제 고객 사례가 포함되지 않는 샘플로 시작한다. 출처 문서 또는 약관을 그대로 공유하기 전 별도 권리와 보안 검토가 필요하다. 360개 수를 채우려고 같은 예시의 숫자만 바꾼 중복을 독립 사례로 주장하지 않는다. 클래스별 분포를 사전 등록하고, 희소한 위험사례는 실제 모집 가능성과 별도 층화 분석을 포함한다.

### 검수와 봉인

- 보험업무 관련 전문가 **2명 이상**이 기준표·출처에 따라 독립적으로 주석을 남긴다. 응답의 정답, 허용 가능한 대안, 불확실성, 심각도, 문단 위치를 기록한다.
- 불일치는 제3 검토 또는 합의로 조정하고, 의견 차이·근거·수정 이력을 보관한다. 참여자와 독립성을 기재한다. 충분한 검수자를 확보하지 못했다면 그 상태를 보고하고 검수 완료라고 쓰지 않는다.
- 케이스/출처/정답/평가기/분할 정의를 동결하고 SHA-256, 버전, 시각, 리뷰 여부를 `dataset_manifest`로 저장한다. 해시만으로 전문가 검수, 생성 과정의 공정성, 법적 권리를 증명하지는 못한다.
- 테스트 담당자는 시스템 구분·정답을 모르게 하고 결과를 수집한다. 가용한 블라인드 범위를 정확히 기재한다. 결과 공개 뒤 변경은 버전업하고 이전 결과를 지우지 않는다.

## 4. 동일 조건 비교안 — 우위는 실험 전 가설

| 변형 | 구성 | 비교 의도 |
|---|---|---|
| B0 | 결정론적 규칙/기본 검증 | AI 없이 해결 가능한 범위와 비용 |
| B1 | 동일 모델의 기본 답변/일반 평가 | 일반 모델·평가의 기준선 |
| B2 | 기존 도구 + **동일** 규정 resolver 및 동일 정답 | 보험 도메인 기능을 기존 도구에 재사용한 비교 |
| T | CaseProof + 같은 모델/문서/권한/리소스 | 전이·승인·증거 워크플로의 추가 효용 가설 |

Langfuse, Phoenix, Promptfoo, Ragas는 성격과 인터페이스가 다르므로 전부 동일 작업을 단독으로 처리한다고 가정하지 않는다. 구현 가능한 경우 trace/eval·security 구성으로 묶어 비교하고, 한 제품에 없는 부분은 동일한 별도 resolver/adapter로 보완한다. 모델·온도·재시도·최대 토큰·도구 권한·timeout·인프라·데이터·정답·검수·측정기간을 사전 등록한다. 결과는 실행자/평가자의 선호와 제품명 노출을 최소화한다.

## 5. 지표와 실패 정책

- 모든 지표에는 케이스 수, 분모, 결측, 실패, 시험군별 비용과 재현 가능한 버전/hash를 제시한다. timeout·연결오류·미완료를 성공 또는 조용한 제외로 다루지 않는다.
- 정답/검출 평가는 위험 양성·음성의 기준을 사전 정의한다. 정답률, 위험 검출 recall(미탐), false positive rate(오탐), 원문 출처 적합성, unsupported claim, 처리 시간, 모델 token/API 비용 및 인프라/검수 인건비를 별도 표시한다.
- 짝지어진 비교는 같은 케이스에서 정답 여부의 차이와 원자료를 기록한다. 95% 구간은 독립 사례·군집 가정에 맞춰 **시나리오 가족 단위 paired bootstrap** 또는 사전에 정한 동등한 방법을 사용하고 seed·반복수·근거를 공개한다. 단순히 두 개의 Wilson 구간을 나란히 놓은 것을 paired difference CI로 부르지 않는다. 표본 수가 부족하면 추정의 불확실성을 명시한다.
- 치명적 오류의 수와 `critical = 사례의 심각도` vs `critical_failure = 그 사례에서 발생한 치명적 실패`를 분리한다. baseline/candidate 어느 쪽이 incomplete여도 비교는 INVALID/INCOMPLETE. 치명적 미검수 사례는 자동 승인 veto. 치명적 오류가 0건이어도 오류 가능성 0이라고 표현하지 않는다.
- 사용성·처리시간은 실참여자와 시나리오를 정의해 관찰한다. 추론 시간이 줄어도 사람이 바로 수정/검토해야 하는 부담이 늘면 함께 보고한다. 투자수익률은 비용·효과 관측 이전에는 가정으로 표시한다.

## 6. 독립 검증과 외부 자료

원본 v5.2 감사 자료는 과거 조사 기록이며 공개 저장소에 재배포하지 않는다. 현재 참고한 공식 기술 문서는 `../docs/SOURCES.md`에 기록한다. 금융위·금융보안원 가이드 첨부 전문 일부와 금융감독원 최종 프레임워크는 당시 직접 열람하지 못했으므로 기준 조항별 매핑 전 원문과 버전을 다시 확보한다. 금융보안원 발표의 17항목은 설계 체크리스트이지 이번 시스템이 평가·인증을 통과했다는 증거가 아니다.

실제 외부 실무자 피드백, 독립 설치, 4종 훈련, 독립 기술리뷰, 제3팩 E2E 자료는 참가자·날짜·환경·원자료·승인 범위를 명시해야 한다. AI가 외부인인 것처럼 가짜 피드백을 만들어선 안 된다.


## v5.3 확정 경계

`08_IMPLEMENTATION_CONTRACTS.md` §§13–15가 이 문서의 데이터 레코드·지표 설명을 구체화한다. CaseInput, CaseMetadata, evaluator-private GoldRecord를 별도 저장하고 model payload는 allowlist로 만든다. 공개 예제와 private blind 120건을 혼동하지 않는다. 실제 reviewer/custodian이 없으면 해당 실험은 SKIPPED다.

미래 비교 API는 어느 한쪽이라도 미완료면 INCOMPLETE와 null metrics를 반환한다. 현재 baseline의 `reference.compare_runs`는 호환 범위에서 INVALID/INCOMPLETE_EVALUATION 및 metrics 미출력으로 보강했다. 둘은 버전 경계가 다르며 상태 이름만으로 서로의 실행 완료를 주장하지 않는다.
