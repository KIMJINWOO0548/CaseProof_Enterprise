# CaseProof Enterprise v5.1 독립 평가 보고서

평가일·검색일: **2026-10-29, 대한민국 표준시(KST)**. 평가 방식: AUDIT ONLY. 별도 평가 산출물 외에 원본 코드, 데이터, 정답, 테스트는 변경하지 않았다. 이 점수는 제공받은 자체 루브릭에 따른 평가자의 점수로 보험사 인사팀이나 금융당국의 공식 평가가 아니다.

## 1. 요약 판정

- **기본 19/100 + 보너스 0/5 = 19/105.** 실행이 필수인 세부 항목에서 이번에 실행하지 못한 증거는 0점으로 처리한 보수적 평가다. 0점이 반드시 코드의 부재나 기능의 실패를 뜻하지는 않는다. 의존성을 확보해 재평가하면 점수가 바뀔 수 있다.
- 49개 표준 라이브러리 기반 단위 테스트, 20개 합성 규칙 사례, Pydantic 스키마, JavaScript 문법과 독립 모의 공격을 확인했다. 원 패키지에서 기록한 **pytest 90개 + 하위 22개 및 smoke 12/12**는 과거 자료이다.
- 이번 `python -m pytest -q`, `python -m scripts.smoke`는 필수 패키지 미설치 및 설치 네트워크 차단으로 실행 실패했다. API·SQLAlchemy·실제 DB 통합에 대한 독립 PASS는 없다.
- **운영 준비도: 출시 차단.** DB 상태 행의 단독 변조로 현업 승인이 빠졌는데도 승인/무결성 성공이 가능한 경로를 원본 함수 추출과 ORM 모의 실험으로 재현했다. 실제 HTTP·DB 재현은 미완료다.
- **채용 포트폴리오 준비도: 개발·DX 공통의 설명 가능한 시제품이지만 즉시 제출 완성본은 아님.** 실행 환경 재현, 본인 기여, 핵심 시연, 실제 AI 연동 여부를 명확히 해야 한다.
- LLM/RAG, 실제 보험약관, 실무자 검수, PostgreSQL/RLS, 브라우저 E2E, 360건 블라인드, WORM, 보안 인증은 미실증이다. 공개 도입 사례는 CaseProof를 해당 보험사가 필요로 한다는 증거가 아니다.

### 평가 범위와 증거 등급

E0 가설 / E1 문서·코드의 정적 명세 / E2 단위·격리 실행 / E3 실제 API·DB·브라우저 통합 / E4 별도의 독립 기관·실무자 또는 환경에서 재현한 외부 검증. 이번 평가자의 제한된 함수 실행을 E4 또는 실제 HTTP 테스트로 부르지 않는다. 등급은 해당 평가축에서 확인된 가장 높은 수준이며, 축 전체가 그 등급을 만족한다는 뜻이 아니다.

### 추가로 확인된 구체 결함

1. **승인 사유 스키마 불일치(E2).** `schemas.py:35–44`에서 `Transition.reason`은 기본값이 있어 `Decision.model_json_schema()['required']`에 빠진다. 그러나 `Decision` 검증은 8자 미만을 거부한다. `logs/schema_validation.txt` 참조. OpenAPI 전체는 미생성 상태여서 HTTP 스펙의 실제 렌더링까지는 미확인이다.
2. **숫자의 bool 강제 변환(E2).** Pydantic 2.14.1에서 `EvalRequest.model_validate({'claim_days': True, ...})`는 1로 변환된다. `reference/verify_answer.py`의 bool 거부보다 앞에서 형이 바뀔 수 있다. FastAPI HTTP 경로의 실제 요청은 미실행이다. 숫자 1을 허용하는 업무팩에서 특히 오판 가능성이 있으므로 strict 처리와 API 회귀가 필요하다.
3. **불완전한 비교 기준선 허용(E2).** `reference/paired_benchmark.py:33–45`가 후보만 `complete` 확인한다. 기준선 한 건이 `complete=False`이고 후보는 완료된 합성 입력에서 `ELIGIBLE_FOR_HUMAN_REVIEW`, 100%p 향상 및 Wilson 구간을 반환했다. **참조 함수의 결함**이며 현 서비스 출시 경로에 연결되었다는 증거는 없다. 양측 완료·결측 처리를 정의해야 한다.
4. **미승인 특약의 기본약관 대체(E2, 도메인 위험).** `resolver.py:72–76`은 미승인 특약도 known으로 보지만 published 필터에서는 제외한다. 합성 특약을 DRAFT로 바꾸어 메모리에서 호출하면 특약 60일 대신 기본 45일을 RESOLVED 한다. 실제 보험법상 반드시 오류라고 확정할 수는 없다. 해당 경우 기본약관 적용 가능 여부를 실무자가 정하고, 불확실하면 INCONCLUSIVE로 처리할 정책과 테스트가 필요하다.
5. **재전송 중복 및 UI/API 불일치(E1–E2).** `app.py:316–337`의 생성 POST에 idempotency key가 없고 격리 모의 호출에서 같은 본문에 2개의 ID가 생겼다. `app.py:345–384`는 ANALYST와 테넌트를 확인하지만 요청자 여부는 확인하지 않는다. 반면 `index.html:32`는 요청자만 평가 UI를 표시한다. 같은 회사의 다른 ANALYST 사용 시 의도된 협업인지 정책을 명확히 하고 실API에서 재시험해야 한다.

## 9. 105점 도달 로드맵

점수는 결과로만 갱신한다. Gate 통과 전 해당 점수를 선반영하지 않는다.

1. **Gate 0 — 안전하고 재현되는 시제품:** 합성 전용 DB, 정확한 현재 디렉터리, 버전 고정 환경에서 90개 pytest 및 12개 smoke와 브라우저 E2E를 새로 실행하고 로그를 보존. 기존 성공 로그의 독립 재현. 실패는 삭제하지 않고 수정 후 재실행.
2. **Gate 1 — 승인 무결성:** P0의 상태/decision/event 불일치와 자기 승인, 테넌트 접근, 중복 요청, 결과·감사 변조, 동시 경쟁을 실제 TestClient + PostgreSQL에서 재현·수정·회귀. DB 역할/RLS, 외부 앵커와 복구까지 증명. 단순 테스트 개수 증가로 가점하지 않음.
3. **Gate 2 — 보험 업무 정답:** 사용 허가가 있는 약관과 변경 이력 또는 실무 검수된 합성 대체자료로 계약·사고·청구 시점, 특약 우선순위, 비승인·소급·문서 혼입의 정답과 불확실성 정책을 수립. 보험 실무자 2명 이상이 독립 검수하고 의견 불일치를 기록·해소. 특정 회사 실제 도입 수요는 인터뷰로 별도 확인.
4. **Gate 3 — 실제 AI와 대조실험:** 개인정보 없는 자료로 실제 LLM/RAG 연결, 출처 추적, 도구 제한 및 prompt-injection/허위 출처 레드팀. 전문가 이중 검수 360건을 봉인·블라인드로 운영하고 동일 모델/질문/정답/지표/예산으로 기존 도구와 paired 실험. 오류·미실행·신뢰구간·비용을 투명하게 보고. 360은 이 루브릭의 요구이며 자체로 통계적 충분성 보장은 아님.
5. **Gate 4 — 현업과 운영:** 접근성·역할별 사용성 시험, 반려·시정·복구, 설치·업그레이드·롤백, 관측, 모니터링, 복구 훈련, 경쟁 도구와 TCO 및 제품 경계 확인. 별도의 보안 점검·규제 적용 검토 및 실데이터 처리 조건은 해당 기관과 확정.
6. **Gate 5 — 외부 5점:** 보험 실무자 2명 서면 리뷰 반영, 독립 Windows 설치, 4종 게임데이, 외부 기술 리뷰, 제3 업무팩 무수정 E2E를 각각 외부 증거와 재시험으로 충족. 충족되지 않은 보너스는 계속 0점. 외부 평가가 낮거나 비교 결과가 불리하면 그대로 반영.
