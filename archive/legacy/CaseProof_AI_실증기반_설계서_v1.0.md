# CaseProof AI — 금융 AI 의사결정 근거·규정변경 검증 플랫폼

**실증 기반 상세 설계서 v1.0 | 작성 기준일: 2026-10-28**  
**목적:** 금융·보험 AI/DX/IT서비스 기획·SW 개발 취업용 포트폴리오 및 공개 가능한 제품형 PoC  
**프로젝트 상태:** 설계 검증 단계. 실제 소프트웨어 구현, 현업 인터뷰, 성능 측정 및 보안 시험은 수행되지 않음.  
**범위:** 공개된 보험 표준약관 및 *가상* 보험사 내부규정으로 만든 테스트 환경. 실제 보험금 지급결정·법률 자문·규제 준수 인증을 수행하지 않음.

## 요약: 무엇을 만들고, 무엇은 만들지 않는가

CaseProof AI는 보험사 AI가 고객에게 제공할 답변 초안이나 업무 안내를 **근거 문서**, **적용 시점**, **규정 버전**, **사전 정의된 업무 정책**과 교차 검증한다. 약관이나 AI 모델이 바뀌면 동일한 검증 사례를 자동 재실행하여 바뀐 결과를 보여 주며, 위험한 답변은 사람이 검토할 때까지 중단한다. 모든 판정에 근거·버전·평가자·원본 해시를 연결해 감사 가능한 보고서를 작성한다.

**우선하지 않는 것:** Munder Difflin 같은 범용 멀티에이전트 오케스트레이터, LLM 모델 자체 학습, 보험금 지급 자동 승인, 실고객 데이터 수집, 금융규제 인증, 범용 AI 관측 플랫폼 새로 개발. Phoenix·Langfuse 같은 검증된 도구를 활용하고 **도메인별 검증 논리와 재현 가능한 평가자료**에 개발을 집중한다.

**핵심 한 문장:** ‘이 AI 답변은 맞는가?’에서 더 나아가 ‘**그 날짜의 그 계약·그 약관 버전에 비추어 맞았으며, 개정 이후에도 안전하게 배포해도 되는가?**’를 확인하는 시스템.

**근거 간 충돌 및 시사점:** 경쟁 솔루션이 범용 평가를 이미 지원한다는 사실은 ‘AI 평가 시장의 필요’와 ‘우리 제품의 차별성’을 동시에 뒷받침하지 않는다. 전자는 뒷받침하지만 후자는 오히려 감점한다. 반면 공식 표준약관의 버전과 적용 시점은 도메인 특화의 실험 가능한 데이터 근거다. 사용자 인터뷰 및 실제 채택 수요는 **미확인**이다.

## 2. 경쟁·오픈소스 대조 및 재사용 전략

| 대상 | 이미 제공하는 기능 | 재사용 방식 | 직접 만들 부분 |
|---|---|---|---|
| Arize Phoenix | OTel 실행 추적, RAG 평가, 데이터셋, 실험, 프롬프트 재실행 | 관측·평가 인프라로 우선 채택 | 보험약관 유효일 검증, 버전별 회귀 리포트, 감사증적 |
| Langfuse | 실행 추적, 평가, 프롬프트 관리, 데이터셋 | Phoenix 대체 후보; 둘을 동시에 필수 설치하지 않음 | 동일 |
| Ragas | Faithfulness, Context Precision/Recall | 보조 평가 메트릭 사용 | 조항번호/유효일/예외조건의 결정론적 검증 |
| Giskard | RAG 테스트셋·구성요소별 성능 진단 | 공격·질문 유형 아이디어 참고 | 보험 규정 변경 기반 회귀 분석 |
| OWASP·NIST | 보안·위험관리 준거 | 테스트 항목·체크리스트에 반영 | 실제 차단·승인 구현 |
| Munder Difflin류 오케스트레이터 | AI 작업 배분·자동화 | 개발 실행 도구로만 활용 가능 | 범용 에이전트 관리기 재구현 금지 |

**차별화 가설 H1:** ‘약관 버전+계약/질의 시점에 맞춘 근거 검증’은 단순 faithfulness보다 보험업무 오류를 더 잘 포착한다. **H2:** ‘규정 개정시 자동 리플레이·배포 차단’은 모델 교체 실험보다 업무운영 가치가 높다. 두 가설은 제품 홍보 문구가 아니라 실험 대상으로 둔다.

## 3. 제품 문제정의와 사용자

**문제 P1 — 시점 오류:** 2025년에 판매한 가상 상품의 계약에 2026년 개정 약관을 근거로 답하는 오류. **P2 — 증거 오류:** 실제 약관과 무관한 조항을 출처로 제시하거나 예외 문장을 생략. **P3 — 변경 영향:** 프롬프트/모델/문서 변경 후 이전에 맞던 답변이 틀리게 되는 현상. **P4 — 검토 불가능:** 어떤 문서와 모델로 답했는지 남지 않아 담당자가 재현하기 어려움.

**페르소나 A (민원 담당자):** 1건의 답변초안을 입력하면 근거 조항, 누락사항, 승인/반려 이유를 보고 싶다. **페르소나 B (AI 운영자):** 새 약관·모델을 배포하기 전에 기존 240개 테스트에서 어떤 결과가 달라졌는지 보고 싶다. **페르소나 C (감사·리스크 담당자):** 버전·검토자·판정 증거를 사후 재현 가능한 묶음으로 내려받고 싶다.

**정의한 JTBD:** ‘모델/문서 업데이트를 요청받았을 때, 보험 소비자에게 부정확한 안내가 나갈 위험을 사전에 파악하고 근거 있는 승인·보류 결정을 내리고 싶다.’

## 4. 좁고 명확한 초기 사용 사례

처음에는 **가상 손해보험 회사의 고객 민원 답변 초안**만 다룬다. 답변 유형은 (a) 청구 서류 안내, (b) 보장·면책 관련 약관 위치 안내, (c) 처리절차·이의제기 방법 설명. 보험금 지급 여부, 보험료 책정, 보험사기 판정, 실제 고객에게 답장 발송은 하지 않는다.

**대표 시나리오:** ① 운영자가 공개 표준약관 원문에서 허용 범위를 선별해 v1/v2 문서 묶음을 등록 ② 가상 계약일·문의일·상품 버전 메타데이터를 포함한 케이스 입력 ③ 외부 AI가 생성한 답변 또는 내장 데모 AI의 초안을 수신 ④ CaseProof가 답변을 문장별 주장으로 분해해 조항·유효기간·근거를 검증 ⑤ `PASS / REVIEW / BLOCK / INCONCLUSIVE` 결정 및 근거 제시 ⑥ v2 공개 시 기준 테스트 리플레이 ⑦ 담당자 승인 이후에만 ‘배포 허용’ 시뮬레이션 상태로 전환 ⑧ 감사용 증거 패키지 다운로드.

### 실패 예시의 핵심

가상 약관 v1에는 ‘접수 기한 30일’, v2에는 ‘접수 기한 20일’이라는 **실제 약관과 무관한 예시**가 있다고 가정한다. 특정 계약은 v1이 적용되도록 테스트 데이터를 만든다. 최신 문서만 검색한 AI가 ‘20일’이라 답하면 일반 검색/생성 평가에서는 맞아 보일 수 있으나, **계약에 적용되는 규정 기준으로는 오답**이다. CaseProof는 `VERSION_MISMATCH`라는 실패 유형과 함께 적절한 v1 조항을 제시한다. 이 숫자는 데모용 합성 규정이며 실제 보험 약관 수치가 아니다.

## 5. 요구사항 — 기능과 비기능

### 필수 기능(FR)

- FR-01: 문서 원본 파일, SHA-256, 출처 URL, 수집일, 공개일, 효력 시작·종료일, 법령/약관 구분, 적용 상품 범위를 저장한다.
- FR-02: 문서 조항/표/페이지 추출 후 원문 위치, 파싱 품질, 누락 페이지를 기록한다. 파싱 불명확 부분은 자동 PASS 금지.
- FR-03: `policy_version_id`, `contract_effective_date`, `question_date`, `jurisdiction`, `product_id` 기반 적용 문서 선택. 우선순위 충돌·효력 불명확 시 `INCONCLUSIVE`.
- FR-04: 입력 답변의 주장 분해(claim extraction), 각 주장별 조항 매칭, 수치/날짜/예외사항 결정론적 검증.
- FR-05: 증거 있는 평가: 원문 인용은 짧은 범위로 제한하고 문서ID·조항ID·버전·페이지를 제시한다.
- FR-06: 평가 결과 4단계 `PASS / REVIEW / BLOCK / INCONCLUSIVE`; BLOCK 또는 INCONCLUSIVE면 자동 배포 금지.
- FR-07: 규정·모델·프롬프트 버전 변경에 따라 고정 데이터셋을 재실행하여 개선·악화·미변경을 비교한다.
- FR-08: 사전 정의한 임계값과 위험 항목에 따른 릴리스 게이트. 승인자는 변경이력과 근거 확인 후 서명성 승인 기록 생성.
- FR-09: 실행 추적, 재시도, 시간 초과, 비용, 성능 메트릭, 품질 추세 보고.
- FR-10: 검토자 수정·오류 정답 라벨을 후속 검증 데이터로 승격하되, 기존 테스트셋 오염을 방지한다.
- FR-11: 감사 보고서 JSON/CSV/PDF 내보내기(우선 JSON/CSV, 문서화된 방식으로 PDF 후속).
- FR-12: 공개 데모에는 **합성 데이터만** 사용하며, 고객 개인정보 입력을 경고하고 업로드 확장자·크기·MIME를 검증한다.

### 비기능(NFR)

- NFR-01: PostgreSQL 단일 DB의 테넌트·역할별 서버측 접근통제 및 다른 테넌트 데이터 격리.
- NFR-02: 검증 건당 메타데이터와 전체 실행 lineage (입력→문서→검색→모델→검증→승인) 연결.
- NFR-03: 재실행 시 동일 문서 해시·프롬프트·모델 버전·설정·데이터셋 버전 기록; LLM의 완전 결정성을 보장한다고 주장하지 않음.
- NFR-04: API 장애나 판정 불능일 때 fail-closed. 데모 화면과 운영 상태를 구분한다.
- NFR-05: 최소비용 설계. API 호출 상한·동시작업 제한·재시도 횟수·일일 예산 경고.
- NFR-06: 한국어 UX, 키보드 조작, 상태를 색상만으로 전달하지 않음. 사용자 테스팅 전 접근성 준수 인증 표현 금지.

## 6. 시스템 아키텍처: 복잡도보다 검증 가능성 우선

```
React/TypeScript Web UI
   │    인증 · 작업 큐 · 버전 비교 · 승인 · 보고서
FastAPI / Pydantic (도메인 API, RBAC, 릴리스 게이트)
   ├─ Ingestion: PDF/문서 파싱 → page/chunk/clause + provenance
   ├─ Policy Resolver: 적용 시점·계약 버전·충돌 확인 (규칙 기반)
   ├─ Evaluator: Claim extraction → 검색 → 규칙 검증 → LLM judge
   ├─ Replay Service: 데이터셋 고정 → 모델/문서 버전별 배치 비교
   ├─ Evidence Export: JSON/CSV + 해시 + 검토자 기록
   └─ Worker: Redis/RQ 작업 처리 · 시간초과 · 비용 상한
   │
PostgreSQL + pgvector / Object storage (로컬 개발에서는 안전한 파일 저장소)
   │
Arize Phoenix + OpenTelemetry (관측 및 평가, 자체 관측 엔진 재구현하지 않음)
   │
LLM Provider Adapter (환경변수/키로 교체, 공개 데모엔 Mock 모드 포함)
```

**기술 선택:** React + TypeScript + Vite + Tailwind/shadcn/ui(필요시), FastAPI + Pydantic + SQLAlchemy + Alembic, PostgreSQL + pgvector, Redis + RQ, Docling(파싱 가능한 문서에 한정), OTel + Phoenix, Pytest + Playwright + Ruff + mypy. 초기에는 복잡한 Graph DB, Kubernetes, LangGraph 다중 에이전트, 외부 금융사 MCP 연결을 넣지 않는다. MVP에서는 단일 LLM 어댑터와 규칙 검증으로 충분하다.

**검색:** 문서의 정확한 조항 번호·유효기간·상품ID를 **먼저 SQL 필터로 좁힌 뒤** dense retrieval 적용. 한국어 키워드 검색 정확도가 부족하면 보완할 것. Vector 점수만으로 적용 문서 버전을 결정하지 않는다. OCR 오류·표 변형 등 텍스트 추출 실패는 `REVIEW` 또는 `INCONCLUSIVE`로 분류.

## 7. 도메인 검증 엔진의 상세 동작

### 7.1 적용 규정 결정 (`PolicyResolver`)

필수 입력: `product_id`, `contract_effective_date`, `question_date`, `policy_version_id`(알면), `document_type`. 조항에는 `document_id`, `revision`, `effective_from`, `effective_to`, `supersedes_id`, `applicability_rule`, `clause_id`, `page`, `source_hash`를 기록한다.

1. `product_id`에 해당하는 문서 범위를 선택한다.
2. 계약·질의 시점 중 어떤 날짜가 적용 기준인지 **문서의 명시적 규칙**에서 판별한다. 임의로 최신 문서만 선택하지 않는다.
3. 범위 내 조항의 효력 구간과 계약 특약 메타데이터를 대조한다.
4. 같은 순위의 상충 조항이 있거나 적용규칙을 모르면 `INCONCLUSIVE` 반환 및 검토 요청.
5. 적용 문서 ID·근거 조항·판정 규칙을 provenance에 저장한다.

중요: 계약 체결일, 사고 발생일, 청구일, 질의일 중 **법적으로 어느 날짜가 적용되는지 상품과 규정마다 다르다.** 공개 데모는 작성한 합성 규칙만 자동화한다. 실제 보험 상품의 법적 판단으로 확대하지 않는다.

### 7.2 답변 검증 (`EvidenceVerifier`)

1. 초안에서 검증 가능한 원자적 주장(claim) 목록 추출: 수치, 날짜, 필요 서류, 예외, 주의사항, 근거 인용.
2. `PolicyResolver`가 선택한 문서 집합에서 근거 후보를 검색한다.
3. 결정론적 검사: 조항 존재 여부, 버전 유효성, 문서 중복·충돌, 숫자·기간 비교, 금지된 자동판정/불필요한 개인정보 노출, 출처 없는 핵심 주장.
4. 보조 LLM 판정: 지지됨 / 반박됨 / 정보부족, 판단근거 출력. LLM 평가는 규칙 엔진의 실패를 뒤집을 수 없다.
5. 심각도 도출: 금융소비자 권익에 영향을 주는 잘못된 청구 기간·면책/보장 단정 등은 critical; 기타는 major/minor. 심각도 사전 정의 및 사람이 검수.
6. `BLOCK` = 규정·시점 충돌이나 치명적 오류; `REVIEW` = 불확실하지만 검토 가능; `INCONCLUSIVE` = 문서·적용규칙 부족; `PASS` = **검증 가능한 범위에서** 정해진 검사 통과. PASS도 법적 적합성 보증이 아님.

### 7.3 규정 개정 회귀 검사 (`PolicyChangeReplay`)

1. 문서 v1, v2의 조항 ID·텍스트 차이를 구조화하고 **개정 영향 후보**를 표시한다. 차이점 표시만으로 법적 효력을 판정하지 않는다.
2. 영향받는 케이스와 필수 고정 회귀셋을 함께 선정한다. 동적 선택만 하면 놓친 회귀가 발생할 수 있다.
3. 이전 산출물, 새 산출물, 이전 근거, 새 근거, 위험등급, 검사 코드를 비교한다.
4. Critical이 새로 발생하거나 미승인 case가 하나라도 있으면 릴리스 `BLOCK`.
5. 변경 영향이 허용범위 안이어도 AI 운영관리자의 승인 기록 없이는 `APPROVED` 전환 금지.

### 7.4 실행 상태 머신

`DRAFT → INGESTED → EVALUATING → (PASS / REVIEW / BLOCK / INCONCLUSIVE) → HUMAN_REVIEW → APPROVED / REJECTED`.

- `REVIEW`는 수정·재검증 후 승인 가능, `BLOCK`은 수정·재실행 필수.
- `INCONCLUSIVE`는 근거 보충·문서 수정 없이는 승인 불가.
- 모든 전이는 서버 측 정합성 검증, 권한 검사, 감사 이력을 남긴다.
- `APPROVED`는 '데모 시스템의 내부 승인'으로, 실제 고객 발송·보험심사 허가를 의미하지 않는다.

## 8. 테스트 데이터와 실험 설계 — 성과를 만들어내지 말 것

### 8.1 자료 수집과 정답 라벨

- **공개 근거:** 국가법령정보센터 표준약관 중 저작권·이용조건을 검토한 공개 자료. 원문 전체를 무단 재배포하지 않고 출처 링크·최소 발췌·파생 메타데이터 중심으로 관리.
- **합성 내부규정:** 생성자가 직접 작성한 12~20개 조항의 보험사 가상 규정 v1/v2; 효력일·예외·개정 전후 차이 명시.
- **합성 문의:** 실제 개인 이름·전화번호·증권번호·병력 등 없이 작성. 패턴 다양성은 실제 민원 자료 접근 없이 제한됨.
- **정답 라벨:** 적용 조항 ID, 판단 기준일, 기대 결과, 예상 오류 유형, human review 필요 여부. 정답·판정 이유를 코드 외 독립 문서로 생성.
- **독립 검수:** 가능한 경우 보험 실무/법규 경험자 검토(미확보); 확보 전에는 '전문가 검증' 표현 금지. 작성자 단독 검증 편향 표기.

### 8.2 최소 240개 사례(설계 목표, 현재 제작 0건)

| 오류/사례 유형 | 개수 |
|---|---:|
| 정상 근거 기반 안내 | 50 |
| 효력일·구약관/신약관 혼동 | 50 |
| 조건부 보장·예외 누락 | 40 |
| 근거 없음·조항번호 착각 | 35 |
| 간접 Prompt Injection | 25 |
| 개인정보·기밀 추출 시도 | 20 |
| 타계약/타테넌트 접근·권한 오용 | 20 |
| **합계** | **240** |

**분할:** 개발 160, 검증 40, 최종 블라인드 40. 각 유형을 층화 배분하고 최종 블라인드는 임계값·프롬프트 조정에 절대 사용하지 않는다. 동일 사례의 문장 변형은 같은 분할에 배정한다. LLM 판정은 동일 입력을 3회 실행하여 분산을 보고하며, 모델/API 버전을 기록한다.

### 8.3 비교 기준과 가설 검증

- B0: 답변의 문자열/기본 규칙 검사만 수행.
- B1: 일반 RAG + LLM faithfulness 판정(정확한 버전 필터 없는 기준선).
- B2: CaseProof 버전·날짜 resolver + 결정론적 검사 + LLM 보조 판정.
- A/B: 같은 케이스·문서·모델·호출 예산에서 B1과 B2 비교. 별도 검증셋·최종 블라인드셋 두 번 보고.
- **H1 성공조건(사전등록 목표):** 버전 혼동 케이스 탐지 recall이 B1보다 +15%p 이상 높고, false positive 상승은 +5%p 미만. 실제 측정 전 '개선' 표시 금지.
- **H2 성공조건:** 가상 규정 v1→v2 변경 사례 중 위험 회귀의 ≥95%를 CI 배포 전에 검출하고, critical 미검출 0건(표본 내)이며, 테스트셋/실험 로그를 재현할 수 있을 것.
- **주의:** 40개 블라인드 표본에서 0건이 나왔다고 실서비스 무오류를 주장할 수 없다. 신뢰구간과 표본 규모의 한계를 같이 기재.

### 8.4 메트릭과 게이트

| 지표 | 산식/의미 | v1 릴리스 목표(가정) |
|---|---|---|
| 버전 오류 탐지 재현율 | 잡은 버전 오류 / 전체 정답 버전 오류 | ≥95% |
| Critical 오류 미탐지 | 놓친 Critical / 전체 Critical | 블라인드셋 0건 |
| 불필요 차단율 | 오답 아닌데 BLOCK인 건 / 정상 건 | ≤5% |
| 근거 조항 정확도 | 정답 조항 ID와 일치 건 / 근거를 제시한 건 | ≥95% |
| 근거 있는 주장 비율 | 근거 지지 주장 / 검증 대상 전체 주장 | ≥95% |
| 승인 추적성 | reviewer·version·timestamp·reason 모두 존재하는 승인 / 전체 승인 | 100% |
| 격리 실패 | 타 테넌트 접근 성공 건수 | 0건 |
| 재현성 | dataset hash·config·model version을 기록한 실행 / 전체 실행 | 100% |
| P95 검증 지연 | eval API 작업의 p95 처리시간 | ≤10초 (환경·예산별 별도 보고) |
| 단위 비용 | 평가 100건당 원화 비용(LLM·인프라 분리) | 측정 후 제시 |

결과는 탐지율만 제시하지 않고 TP/FP/FN/TN, 분모, 단위, 데이터 분할, 모델명, 테스트 환경, 실패 예시를 포함한다. LLM-as-judge와 사람이 채점한 40건 이상의 일치율도 별도 보고한다. 미달 시 포트폴리오의 결과 보고서를 수정하고 의도적으로 점수 조작하지 않는다.

## 9. 실서비스를 흉내 낸 금융권 통제·보안 설계

- **권한:** `ADMIN`, `AI_OPERATOR`, `REVIEWER`, `AUDITOR`, `VIEWER`. 감사자는 원본 수정·승인 불가; 승인자는 본인이 등록한 위험 변경을 단독 승인하지 못하도록 시뮬레이션할 수 있다.
- **기본 차단:** 허용되지 않은 URL/툴 호출 금지, 외부 시스템 쓰기 불가, 모든 고위험 작업 사람 승인, 고위험 응답은 fail-closed. 프롬프트의 '승인해줘' 지시로 권한 상승 불가.
- **데이터:** 모든 공개 시연 입력은 합성 데이터. PII 탐지·로그 마스킹, API 키 서버측 보관, 암호화 전송, 업로드 제한, 데이터 보존·삭제 정책.
- **감사:** 원문 파일 해시, 파싱 버전, 조항 ID, 추출 결과, 판단 상태, 승인자, 시각, 모델/프롬프트/코드 버전을 결합하여 서명 가능한 JSON 보고서. 단순 해시 목록 자체를 변조불가라고 주장하지 않는다.
- **공격 시험:** 악성 PDF/약관 내 '이전 지시 무시' 삽입, 조항 출처 위조, 다른 상품 접근, 가격/토큰 고갈, 출력 HTML 주입, 멀티테넌트 ID 바꿔치기, 문서 버전 교체, 제3자 라이브러리 취약점.
- **보안 기준:** OWASP LLM Top 10 2025, OWASP API BOLA, 금융 AI 7대 원칙, 금융보안원 평가항목에 대응하는 통제·테스트 매트릭스 작성.
- **법적 한계:** 가이드라인은 일부 원칙이 자율규제 성격이며 실제 적용법규는 시스템 기능·업무범위에 달려 있다. 본 설계는 준법 검토 보고서가 아닌 연구용 구현안이다.

## 10. 화면 설계 — 면접에서 보여줄 6개 화면

**S1 운영 Overview:** 검증 요청수, PASS/REVIEW/BLOCK, 버전 충돌 상위유형, 일별 품질 변화, 최신 릴리스 상태. ‘현재 운영’으로 오인되지 않도록 DEMO 배지 사용.

**S2 케이스 검증 상세:** 좌측 민원문/AI 답변, 가운데 주장별 판정과 위험도, 우측 원문 조항/페이지/해당 버전/효력기간. 답변 내용 클릭 시 해당 근거 스크롤; 불일치 부분 강조. 정답 미확정 케이스는 회색 ‘판정불능’으로 표시.

**S3 규정 버전 관리:** v1/v2 문서 선택, 개정된 조항 테이블, 효력일, 영향받는 케이스 개수, 잘못 연결된 출처 경고, 실행 가능한 ‘영향도 다시 검사’ 액션.

**S4 회귀 테스트:** B1 대비 B2 정확도, 새 버전 개선/악화, Critical 차단 내역, 특정 케이스의 이전/현재 근거 Diff, 실행 설정과 비용 비교.

**S5 검토 및 승인:** 위험 순서 대기열, 승인/반려, 사유 입력 필수, 수정 후 재검증, ‘고위험 항목은 승인 전에 재검증 필수’ 정책, 역할 별 액션 노출.

**S6 감사 보고서:** 데이터셋 해시, 문서 원본 해시, 변경 전후 지표, 담당자·시각·근거, CSV/JSON 다운로드. 증거 링크 누락시 보고서 실패 표시.

**UX 성공 기준:** 2분 데모에서 (1) 오답이 왜 차단되는지, (2) 옛 약관/새 약관 문제가 어디서 발견되는지, (3) 사람의 최종 검토가 어떻게 동작하는지, (4) 어떤 수치로 개선이 증명되는지가 설명 가능해야 한다.

모든 외래키가 기관 경계를 침범하지 않도록 DB 및 API 계층에서 강제한다. 삭제 정책은 soft delete 또는 공개 데모 초기화를 문서화한다. 원문 전체·개인정보를 telemetry에 기본 전송하지 않는다.

## 12. 테스트 전략과 구현 완료 기준

**단위 테스트:** 유효일 경계 포함/제외, 중복 개정 조항, 예외와 특약, 숫자·단위, 상태 머신의 금지 전이, permission matrix, 비용 제한.

**통합 테스트:** PDF 업로드→조항 저장→규정선택→평가→사람승인→감사 내보내기 end-to-end, 재시도와 작업자 재시작, API 타임아웃, 제3자 모델 장애 시 차단.

**E2E:** Playwright로 6개 화면 주요 경로 및 키보드 사용 검증. `BLOCK`에 승인 버튼 노출 금지, 문서 누락 시 `PASS` 미표시.

**공격 테스트:** 직접·간접 프롬프트 인젝션, 타 계정 실행결과 조회, URL injection, 악성 파일, 비용 고갈, 마스킹 실패, 개인정보가 실행 추적에 남는지 확인.

**운영·신뢰성:** Docker Compose로 1명 노트북에서도 원클릭 데모, 더미 계정 세트, 자동 테스트 및 헬스체크, 백업·복구 시연, 장애 시 fail-closed 확인.

**출시 차단 게이트(모두 필수):**
1. 모든 핵심 검증·권한·상태 머신 테스트 통과.
2. 블라인드셋 결과가 설계 임계값 충족 또는 임계값 미달 사유·리스크를 명시하고 ‘연구용 미완성’으로만 공개.
3. Critical 오류 미탐지 0건(해당 테스트셋 범위 내), 승인 없는 고위험 배포 시뮬레이션 0건.
4. 개인정보 노출·테넌트 권한 우회 테스트 0건 성공.
5. 테스트·계측 로그·실패 사례·실행 방법·한계 문서 공개.

## 13. 실행 순서: 주차가 아니라 검증 게이트 기반

**Gate 0 — 조사/자료 승인:** 공식 문서·대체재 비교·제품 가설·테스트 실패 유형 확정. 조항 인용·공개 사용조건 확인. 산출물: research.md, ADR-001, data_policy.md.

**Gate 1 — 진짜 동작하는 세로 슬라이스:** 2개 합성 약관 버전, 10개 케이스, 단일 평가 API, `VERSION_MISMATCH` 검출, S2 검증 상세 화면. 외부 LLM 실패 시에도 규칙 검사 시연 가능. 이것이 첫 데모.

**Gate 2 — 평가 재현성:** 100개 사례/고정 셋, B1/B2 비교, TP/FP/FN/TN 리포트, Phoenix trace, 데이터셋/설정 해시. 성능이 나쁘면 모델 튜닝보다 규정선택 오류부터 수정.

**Gate 3 — 운영 통제:** 5개 역할, 승인/반려, 상태머신, RQ/Redis 재시도, 감사 JSON 내보내기, 타 테넌트 접근 차단.

**Gate 4 — 차별화 입증:** v1→v2 개정 영향 탐색, 240개 데이터셋과 40개 블라인드셋, 실제 회귀 검출 실험, 기존 도구 대비 차별성 표.

**Gate 5 — 공개/포트폴리오:** 데모 배포, 동작 영상, README, 아키텍처/ADR, 위협모델, 평가 결과·오류 사례, 2분/10분 면접용 시연자료, 재현 가능한 테스트 명령.

**범위 축소 규칙:** Gate 2까지 재현 가능한 기준선을 확보하지 못하면 멀티에이전트·MCP·OCR 고급화·Graph DB·거대 대시보드 추가 금지. 사용성 개선이 필요해도 핵심 검증이 먼저다.

## 14. 100점 평가표: 검색 근거와 직접 연결

이 평가표는 **실제 채용담당자 또는 금융사로부터 부여받은 점수가 아니라**, 조사 결과를 근거로 작성한 설계 평가 루브릭이다. 점수는 객관적 데이터가 아니라 '점수 부여 규칙과 증거'가 투명한 전문가 판단이며 실험 결과는 별도다.

| 평가 영역 | 배점 | 현재 설계 점수 | 근거·감점 이유 | 100점 조건 |
|---|---:|---:|---|---|
| 실제 금융사 수요·채용 적합성 | 15 | 14 | R01/R02/R04/R05로 수요 방향 확인; 현업 인터뷰·채택 의향 없음(-1) | 현업 3명 이상 인터뷰 및 문제 우선순위 검증 |
| 경쟁제품 대비 차별성 | 15 | 12 | R06/R07에 범용 기능 존재; 버전/시점 검증 가설 미실증(-3) | 동일 데이터에서 범용 기준선보다 명확한 오탐·미탐 개선 입증 |
| 보험 도메인 요구사항 정밀성 | 15 | 13 | R03과 합성 유효일 규칙 설계; 실제 상품 특약/계약 법리 검증 없음(-2) | 공식 출처·적용시점·조건별 전문가 검토 완료 |
| 아키텍처·실행 상세성 | 15 | 14 | API·스키마·상태·게이트 명세; 실제 구현 적합성 미검증(-1) | 구현 후 ADR·API 스펙·실행 증거 확인 |
| 공정한 정량 검증체계 | 15 | 12 | R08 등 측정규칙 지정; 골드셋·블라인드 실측 없음(-3) | 사람 검수 라벨·반복실험·신뢰구간·재현 리포트 확보 |
| 금융 AI 통제·보안 | 10 | 9 | R01/R02/R09/R10 통제 대응; 침투 테스트 없음(-1) | 필수 위협 테스트·접근통제·감사 검증 통과 |
| 1인 개발 실현 가능성 | 10 | 9 | 범용 플랫폼을 제외한 수직 범위; PDF 품질/성능 리스크(-1) | 1인 환경에서 자동화 E2E 및 비용 상한 검증 |
| 포트폴리오 전달력 | 5 | 3 | 명확한 2분 시연 구조; 실행 가능한 배포·영상 없음(-2) | 실제 작동 데모·공개 코드·테스트 결과·시연 영상 |
| **합계** | **100** | **86** | **조사·설계 수준의 잠정 평가** | **모든 증거와 검증 게이트 충족 시 100점 가능** |

**주의:** 86점은 제품 품질이나 채용 합격 가능성이 아니라 **현재 문서에서 입증한 설계 준비도**다. 실제 코드가 전혀 없으므로 제품의 실측 성능 점수는 **미평가**다. 앞으로 점수를 높이는 유일한 합리적 방법은 표에 적힌 증거를 채우는 것이지, 근거 없이 점수를 다시 매기는 것이 아니다.

### 우선순위가 높은 감점 제거 작업

- **-3 차별성:** 문서 날짜가 다르면 B1(범용 RAG)은 통과하고 B2가 차단하는 *동일 케이스* 20개 이상을 미리 설계해 공정하게 실험.
- **-3 정량 검증:** 오답·정답 라벨 생성, 사람이 독립 검수, blind holdout과 3회 반복, 95% 신뢰구간 또는 표본한계 설명.
- **-2 도메인 정밀성:** 가상 상품/약관으로 법적 판단 혼동 없도록 룰을 명시하고 공식 자료에 연결되는 설명서를 작성.
- **-2 전달력:** 눈으로 보이는 첫 데모, 설치 자동화, 실패 예시 중심 2분 시연.
- **나머지 -4:** 취업 관점 현업 인터뷰, 파싱 품질, 보안 시험, 구현 검증.

**AI 구현 지침:**

1. `AGENTS.md`에 본 명세, 우선순위, 범위 제외, 실패시 기본차단 원칙, 평가 게이트를 단일 정본으로 등록.
2. 코딩 전 기존 저장소·자료·툴을 조사하고 중복 구현을 피함. API 계약·데이터 스키마·테스트를 먼저 작성.
3. 첫 작업은 Gate 1. 반드시 `VERSION_MISMATCH`를 검출하는 재현 가능한 pytest와 한 페이지 데모 완성.
4. 데이터·규정·프롬프트·평가 코드를 변경할 때마다 관련 회귀 테스트 및 baseline 비교. 임의 점수 상승 금지.
5. 테스트 실패, 기능 미구현, 규제 불확실, 외부 자료 부족은 보고서에 `미완성/미확인`이라고 표기.
6. 기능별로 요구사항 ID, 테스트 케이스, 변경 커밋, 데모 스크린샷을 연결. 자동으로 개인정보 입력/실서비스 연동 금지.
7. 외부 도구·플러그인·MCP는 필요성과 권한을 검토한 뒤 최소한으로 연결. Munder Difflin은 *개발 조정 도구*로 활용 가능하지만 프로젝트 기능과 혼동하지 않음.

**초기 완료 명령이 아니라 완료 조건:** `docker compose up --build` 실행, `pytest` 통과, 웹 UI에서 합성 케이스 10건 검증, 버전 오류 1건 이상 차단, 데이터 파일·원문·API 키 비노출, 실행 결과 JSON 내보내기. 실제 실행 확인 전에는 '완료' 표시 금지.

## 17. 채용 면접/포트폴리오에 제시할 산출물

**문제 정의:** KB손해보험 AI Agent 활용 사례와 금융 AI 평가기준을 비교해 '적용 시점/문서 개정 후 답변 오류'를 실험 대상으로 좁힘.  
**기술 기여:** 계약 시점별 PolicyResolver, 근거 검증, 규정 변경 회귀 테스트, 위험별 승인 게이트, 독립 골드셋.  
**실험:** 범용 RAG vs Version-aware 검증의 혼동행렬·개선과 실패 사례.  
**제품 역량:** 동작하는 React 대시보드, API 설계·배포, 감사 보고서, 비용 측정.  
**윤리적 설명:** 금융사의 실제 내부 시스템 구현이나 고객 데이터 활용 경력이라고 표현하지 않음. 개인 프로젝트·시뮬레이션·합성 데이터임을 명확히 표기.
