# 02. 보험사 실제 운영을 가정한 검수자용 인수 기준

## 현업 페르소나 / 사실로 검증할 일

- **규정 담당자(Policy Owner)**: 개정 약관 원본·상품·특약·적용 계약을 등록. 정본/출처 이력은 실제 전자결재와 연결해야 함(미구현).
- **AI 업무개선 분석가(Analyst)**: 변경 등록, 규정별 테스트, 오류 분석. 2개의 PASS 검증이 있다고 해서 고객 피해 위험이 사라지는 것은 아님.
- **보험업무 검토자(Domain Reviewer)**: 적용 시점과 문서 근거·약관 범위·고객상황을 검수. 수정 권한과 별도의 승인 권한 구분.
- **IT 릴리스 승인자(Release Approver)**: 시험 스냅샷, 업무 책임자 승인, 치명적인 미해결 결과, 추적 가능성 확인.
- **내부감사(Auditor)**: 어떤 버전의 어떤 자료가 승인 근거였는지 독립적으로 재현.
- **보안 담당자(Security Officer)**: 인증·개인정보·감사·비상 중지, 위임도구 최소 권한 검증(향후).

## 규정 판정의 정확성 문제

시간축을 단일 `basis_date`로만 보존하는 시스템은 실제 청구 시스템으로 사용할 수 없습니다. 계약 체결일, 사고 발생일, 보험금 청구일, 특약 가입일, 해지·부활, 적용 약관 정본 승인일 등이 서로 다르기 때문입니다. 다음 설계에서 상품별 날짜 근거를 `DateBasisPolicy` 구조로 명시하고, 유효시점과 시스템 등록시점(bitemporal) 및 이벤트 시점의 자료 스냅샷을 분리합니다. **어떤 날짜를 쓰는지 판단하는 일은 상품·법무 담당자의 책임**으로 남깁니다.

## 운영 장애시 실패 처리

- DB 연결 불가: 503/서비스 불가, 읽기캐시로 승인 금지 (현재 구현되지 않은 계획).
- 평가기 해시 변경: 현재 요청 생성/검토 차단. 다음 단계: migration 승인 체계와 버전별 비교.
- 감사 체인 손상: 409 승인 차단, incident 발생·관리자 조사 필요. 현재는 자동 알림/사고 티켓 연동 없음.
- 승인 중 통신 끊김: 결과 조회로 상태 확인; revision 값 기반 재시도·멱등 헤더는 평가에만 구현, 승인 API 멱등성 미구현.
- 개인정보 입력 시도: 현재 로컬 합성 데모로만 사용. 실제 고객 데이터 입력 금지 안내와 물리적 망 분리가 필요.
