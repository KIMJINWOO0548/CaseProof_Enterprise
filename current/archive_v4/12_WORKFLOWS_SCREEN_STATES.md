# 실무자가 매일 쓰는 화면·상태·예외 명세 v4

## 1. 역할·출근 후 업무 흐름

| 역할 | 첫 진입 | 즉시 봐야 할 것 | 누를 수 있는 것 | 절대 해서는 안 되는 것 |
|---|---|---|---|---|
| 업무분석가 | '내 검증 업무' | 최근 오류·미검증 답변·기한 | 사례 등록, 검증 실행, 검토 요청 | 스스로 출시 승인 |
| 보험상품 책임자 | '문서 검수함' | 개정 약관·원문 조항 | 규정 승인/반려 | AI 배포 승인 대체 |
| 현업 검토자 | '검토 대기함' | 오류 이유·관련 조항·비교판정 | 도메인 정합성 승인/반려 | 자신이 작성한 문건 최종 출시 승인 |
| AI 리스크 담당 | '위험 검토' | CRITICAL·보안·드리프트 | 위험 검토 서명·예외 요청 | CRITICAL 무시·자동 패스 |
| IT 배포 승인자 | '릴리스 후보' | 테스트 커버리지, diff, 책임자 | 배포허가/반려/회수 요청 | 자기 요청 자기 승인 |
| 내부감사 | '감사센터' | 누가 언제 무슨 증거로 승인 | 비식별 보고서 내보내기 | 운영 데이터 수정 |
| 조직관리자 | '조직관리' | 부서별 권한·테넌트 | 인력 권한 관리 | 본인 권한으로 무단 승인 |

역할은 복합으로 부여할 수 있지만 승인 요청자·소유자와 승인자는 **개인 ID 기준** 분리해야 한다.

## 2. 핵심 사용자 여정 (실제 업무 절차)

### WF-101 새 약관 등록과 게시 (상품 담당자)
1. 파일 업로드: PDF/공개 약관. 바이러스 검사·크기·MIME 허용 확인, 원본 SHA-256 저장, `QUARANTINED`.
2. 문서 추출: 조항 위치, 표/주석, 원문 페이지/좌표, 추출기 버전, OCR confidence. 실패 시 `PARSE_FAILED` + 재처리.
3. 개정 비교: 신구 조항 diff 표시, 적용시점·상품·특약 연결. **규정 번호 충돌, 누락 페이지** 자동 표시.
4. 검수자가 각 변경 조항의 날짜 기준(계약일/사고일/청구일/문의일)과 범위를 승인. 모호하면 `NEEDS_DOMAIN_DECISION`.
5. 승인 후에만 `PUBLISHED`. 본문 수정 시 기존 버전 덮어쓰기 금지, 신규 개정 생성.
6. 새 규정 게시가 활성 AI 답변에 영향을 주면 영향 분석 작업 자동 생성. 알림 실패해도 작업 outbox에서 재시도.

### WF-102 잘못된 AI 답변 접수 (상담/QA 담당자)
1. 대화/모델 출력 수신. `RECEIVED`→`VALIDATED` 또는 `REJECTED_SCHEMA`.
2. 민감정보 마스킹과 테넌트 컨텍스트 검사. 마스킹 실패 시 안전 경로 보류, 로그에는 원문을 남기지 않음.
3. 평가 요청을 분리된 큐에 기록; `idempotency_key`, 추적 ID, 입력 스냅샷 해시 고정.
4. Policy Resolver가 시점·특약 확인. 미결정인 경우 답변을 '정답'으로 취급하지 않고 `INCONCLUSIVE` 표시.
5. 위험 엔진: `CRITICAL`: 다른 상품/테넌트 자료 인용, 보장 여부 확언 오류, 미승인 약관 인용 등. 원문·차이·권한 원인을 한 화면에 표시.
6. 현업 검토자는 원문을 옆에 띄워 '정정 필요 / 추가 자료 / 오류 아님'을 입력. 이유 필수. 그 결과는 새로운 평가 라벨 후보가 되며 원본 라벨은 별도로 보존.

### WF-103 AI 변경·릴리스 승인 (AI PM + 도메인+리스크+IT)
1. 변경 요청 등록: MODEL/PROMPT/POLICY/RETRIEVAL/CODE/TOOL_PERMISSION 중 유형, 영향 상품, 검증 책임자.
2. 이전·신규 artifact SHA 고정, 종속 그래프 기반 테스트 후보 산출, 누락 노드는 강제 수동 검토.
3. A/B 동일 데이터셋으로 paired experiment. 완료되지 않은 실험을 PASS처럼 표시하지 않음.
4. 결과: (A) 평균품질/비용/지연시간, (B) 신규 CRITICAL 목록, (C) 이전 실패 개선 목록, (D) 미검증 범위.
5. 도메인 검토 후 AI 리스크 검토. 치명적 신규 오류 있으면 **자동 BLOCK**, 예외로 우회할 수 없도록 설계.
6. IT 릴리스 승인자는 업무 요청자와 달라야 하며, 승인 시 증거 해시·버전·사유를 저장. 다중 동시 클릭 시 409 STALE_REVISION.
7. 승인 후에도 '실배포'는 외부 CI/CD 별도 권한(선택). CaseProof 자체가 보험사 운영 모델을 배포하지 않는다.

### WF-104 실제 사고·사후 감사
1. AI 문제 발생 보고 → 해당 프롬프트·모델·규정 버전·신규 변경 중지.
2. 위험도 분류 후 담당자에게 통보. 정보유출 의심 시 내용 전송 중단, 키 격리, 침해대응 프로세스 연결.
3. 과거 동일 artifact 기준 재실행, 당시 소스의 recorded time까지 복원.
4. 사고 분석 보고서: 원인, 탐지 시점, 영향범위, 고객 영향 **추정/확정 구분**, 개선 변경안.
5. 블라인드 평가셋에 회귀 사례 신규 등록(원본은 보호됨); 재현 테스트 통과 후 재배포 승인.

## 4. 상세 화면 계약: UI-03 '이 답변이 왜 위험한가'

- 상단: 고객정보는 가상 ID만, 업무명·상품·증빙 상태·최근 평가 실행일·정책 버전.
- 왼쪽: AI 답변에서 `claim_span` 하이라이트. 예: `접수기한은 20일입니다`.
- 가운데: 연결된 원문 조항/페이지/해시, 당시 적용 버전 v1, 신버전 v2. `contract_start_date` 등 기준 날짜를 명시적으로 노출.
- 오른쪽: 규칙 판단 `BLOCK / REVIEW / PASS / INCONCLUSIVE`, 사유코드(읽을 수 있는 한국어), 대응 방법.
- 하단 CTA: `추가정보 요청`, `정정 요청`, `위험 보고`, `검토 완료`. **승인 버튼을 이 화면에 두지 않는다.**
- 실패: 해당 조항 누락·파서 실패·유효일 없음 → `INCONCLUSIVE`이고 고객에게 답변을 내보내는 실행 경로 차단.
- 네트워크 오류: 폼 입력을 잃지 않되 서버 승인 여부가 불확실하면 `재시도 이전 상태 확인` 제공; 브라우저 로컬에 민감내용 저장 금지.
- 접근성: 본문 확대 200%, 키보드 탐색, 툴팁 없이 사유를 텍스트로 전달, WCAG 2.2 AA 목표.

## 5. 화면 공통 상태 기계

```
RECEIVED -> VALIDATED -> QUEUED -> RUNNING -> COMPLETED
     |          |          |         |          |
 INVALID      HOLD      CANCELLED   FAILED     REVIEW_REQUESTED
                                                |
                                        DOMAIN_REVIEWED
                                                |
                                          RISK_REVIEWED
                                                |
                                         RELEASE_PENDING
                                          /     |     \
                                     BLOCKED  APPROVED  REVOKED
```

- `COMPLETED`는 '평가 실행 완료'이며 `PASS` 의미가 아님.
- `PASS`는 판단 내용만. `APPROVED`는 권한 보유자의 별도 승인 이벤트.
- `FAILED` 작업도 실패 이유·재처리 횟수·트레이스 ID 남김.
- `REVOKED` 출처가 쓰인 이전 승인물은 재심사 큐에 등록.
- API 멱등성: 동일 `tenant+idempotency-key+payload-hash`는 이전 결과, 동일 key 다른 payload는 409.
